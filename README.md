# Clean Architecture with Postgres

`capg` is a Go command-line tool that generates model, repository, PostgreSQL
connection, and migration scaffolding for a Go project. The generated code is a
starting point: review and adapt it to your application's schema and needs.

## Requirements

- Go 1.25 or later to build `capg`.
- A Go module in the directory where you run generation commands. The tool reads
  `go.mod` from the current directory; help commands also work outside a module.
- PostgreSQL to use the generated database code.

## Build and install

Build the binary without elevated privileges:

```sh
make
```

Install to `/usr/local/bin` (this usually requires `sudo`):

```sh
make install SUDO=sudo
```

The build runs as the current user; `sudo` is used only for installation. An
existing `/usr/local/bin/capg` will be replaced. Alternatively, install without
`sudo` into your home directory:

```sh
make install PREFIX="$HOME/.local"
```

Ensure `$HOME/.local/bin` is on your `PATH` to run `capg` from the shell.

## Getting started

From the root of an existing Go module:

```sh
capg entity Product
go mod tidy
```

This creates `internal/models/product.go`, `internal/repository/product.go`,
and a pair of migrations for the `products` table, along with missing shared
database and migration files. Review the generated SQL before applying it.

`go mod tidy` resolves the generated imports, including `github.com/jmoiron/sqlx`,
`github.com/lib/pq`, and `github.com/golang-migrate/migrate/v4`. It also updates
the target project's module files for its other imports.

## PostgreSQL example: adapting an entity

This example continues from [Getting started](#getting-started), with `Product`
already generated. It adds a name to the model and table, then implements a
repository method to find a product by name. Use a disposable PostgreSQL database:
the initial migration creates `text*` domains, which must not already exist.

1. Add the `Name` field to the generated `Product` struct in
   `internal/models/product.go` (keep the existing fields and methods):

   ```go
   Name string `db:"name"`
   ```

   The `db` tag maps the field to the PostgreSQL column and lets the generated
   `Save` helper include it in inserts and updates.

2. Before applying the generated migration, add a `name` column to
   `migrations/pg/migrations/*_create_products.up.sql`. The complete table
   definition becomes:

   ```sql
   CREATE TABLE "products" (
       "id" BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
       "name" TEXT NOT NULL,
       "created_at" TIMESTAMP NOT NULL,
       "updated_at" TIMESTAMP NOT NULL,
       "deleted_at" TIMESTAMP
   );
   ```

   The generated down migration already drops the whole table, including the new
   column and its data. Review both files before applying them. If the original
   migration has already been applied, do not edit it; instead, use
   `capg migration add_product_name` and write appropriate up and down SQL for
   the existing data and schema.

3. Add the following method to `internal/repository/product.go`. The generated
   file already imports `context`, `models`, and `pq`:

   ```go
   // ByName returns the newest active product with the given name.
   func (r *Product) ByName(ctx context.Context, name string) (models.Product, error) {
       var product models.Product
       query := "SELECT * FROM " + pq.QuoteIdentifier(r.table) +
           " WHERE name = $1 AND deleted_at IS NULL ORDER BY id DESC LIMIT 1"
       err := r.db.GetContext(ctx, &product, query, name)
       return product, err
   }
   ```

   The name is passed as a query parameter. Like the generated `ByID`, this
   method excludes soft-deleted rows and returns `sql.ErrNoRows` if no row
   matches. If multiple active products share a name, it returns the one with
   the highest ID. Adapt that behavior or add a database constraint to suit
   your application.

4. Create `cmd/example/main.go`. Replace `example.com/shop` in the imports with
   the module path from your `go.mod`:

   ```go
   package main

   import (
       "context"
       "fmt"
       "log"
       "os"

       "example.com/shop/internal/db"
       "example.com/shop/internal/models"
       "example.com/shop/internal/repository"
       pg "example.com/shop/migrations/pg"
   )

   func run() error {
       dsn := os.Getenv("DATABASE_URL")
       if dsn == "" {
           return fmt.Errorf("DATABASE_URL is required")
       }

       ctx := context.Background()
       conn, err := db.Connect(ctx, dsn)
       if err != nil {
           return err
       }
       defer conn.Close()
       if err := pg.MigrationUp(ctx, conn.DB, "migrations/pg/migrations", 0, false); err != nil {
           return fmt.Errorf("apply migrations: %w", err)
       }

       products := repository.NewProduct(conn)
       product := &models.Product{Name: "Notebook"}
       if err := products.Save(ctx, product); err != nil {
           return err
       }
       found, err := products.ByName(ctx, product.Name)
       if err != nil {
           return err
       }
       fmt.Printf("created and found product ID %d, name %q\n", found.ID, found.Name)
       return nil
   }

   func main() {
       if err := run(); err != nil {
           log.Fatal(err)
       }
   }
   ```

5. From the module root, resolve imports and run the example using a DSN for the
   disposable database:

   ```sh
   go mod tidy
   export DATABASE_URL='postgres://USER:PASSWORD@localhost:5432/DATABASE?sslmode=disable'
   go run ./cmd/example
   ```

   Replace the DSN placeholders with your database credentials and settings.
   `sslmode=disable` is for a trusted local setup, not a production default. On
   success, the program prints the product ID and name. Each run inserts a new row.

## Transactions

Generated repository constructors accept either `*sqlx.DB` or `*sqlx.Tx` through
`db.Executor`. Pass the same transaction to every repository and helper involved
in one unit of work. For example, after generating both `Product` and `Order`:

```go
func saveBoth(ctx context.Context, conn *sqlx.DB) error {
    tx, err := conn.BeginTxx(ctx, nil)
    if err != nil {
        return err
    }
    defer tx.Rollback() // releases the transaction if an earlier step fails

    products := repository.NewProduct(tx)
    orders := repository.NewOrder(tx)
    if err := products.Save(ctx, &models.Product{}); err != nil {
        return err
    }
    if err := orders.Save(ctx, &models.Order{}); err != nil {
        return err
    }
    return tx.Commit()
}
```

The caller owns the transaction and is responsible for committing or rolling it
back. Do not mix repositories using `conn` and `tx` for operations that must be
atomic. The context passed to `BeginTxx` controls the transaction lifetime;
individual methods also receive their own context. A cancelled operation returns
an error, and the caller must handle the transaction appropriately.

Database rollback does not restore Go objects: IDs and timestamps assigned during
a rolled-back insert remain in memory. PostgreSQL sequence values can also be
consumed even when a transaction is rolled back. Discard or reset affected model
values before reuse.

## Commands

Run commands from the root of the target module. Each `name` must be a valid Go
identifier that can form an exported type name, such as `Product` or `product`.
Commands list files they create. Use `--dry-run` to preview planned files and
check for known conflicts without writing files or creating directories:

```sh
capg entity Product --dry-run
capg migration add_product_price --dry-run
```

The actual migration version may differ if time or existing files change before
the real run. A dry run cannot guarantee that a later write will succeed.

When generation fails, the error identifies the invalid name, conflicting path,
or blocking migration version where applicable, and suggests a next step. Review
existing files and migration history before moving files or changing versions;
never rename an applied migration without a database migration strategy.

### Entity and repository

```sh
capg entity Product
capg e Product                    # alias
capg entity Product --simple      # or -s
capg entity Product --empty       # or -e
capg entity Person --table people # override the table name
```

- By default, the model has ID, creation, update, and deletion fields. Its
  repository includes `ByID`, `ByIDIncludingDeleted`, `Save`, `Delete`, and
  `Restore`; its migration creates matching columns. `ByID` excludes soft-deleted
  rows; `ByIDIncludingDeleted` includes them. `Delete` and `Restore` update
  `deleted_at` and `updated_at`. Both return `sql.ErrNoRows` if no row is in the
  required state (including repeated deletion or restoration). `Save` returns
  `sql.ErrNoRows` when an update targets a missing or soft-deleted row; use
  `Restore` to restore a deleted row.
- `--simple` generates a model with an ID only and a minimal repository with a
  `Table` method; it does not generate CRUD methods. Its migration creates an
  ID-only table.
- `--empty` generates a model without fields, a repository, or a table migration.
- `--simple` and `--empty` cannot be combined.
- `--table` overrides the table name in both repository and migration. Use 1–63
  lowercase ASCII letters, digits, or underscores, starting with a letter or
  underscore. It cannot be combined with `--empty`.

All three variants also create missing shared database and migration files.
Existing model and repository files are not overwritten: a conflicting file
causes the command to fail. Existing shared files are preserved. Database helpers
accept a single raw table name such as `products` or
`order`: helpers validate and quote it themselves. Do not pass SQL quotes,
expressions, or schema-qualified names such as `public.products`. Names use at
most 63 bytes, start with a letter or underscore, and contain only letters, digits,
and underscores.

### JSON array

```sh
capg array Tags
capg a Tags                       # alias
```

Generates a model type backed by `[]string`, with SQL `Scan` and `Value`
methods. Adapt the element type if necessary.

### JSON structure

```sh
capg struct Settings
capg s Settings                   # alias
```

Generates a model with example fields and SQL `Scan` and `Value` methods. Replace
the example fields with the structure needed by your application.

### Migration scaffolding

```sh
capg migrate
capg m                            # alias
```

Creates missing migration support files without overwriting existing ones. This
command generates files; it does not connect to PostgreSQL or run migrations.
For a new setup, the initial `types` migration receives the local creation time
minus one clock minute, in `YYYYMMDDHHMM` format. If existing versions are at or
after that value, its version is advanced to a later minute. Entity migrations start at the
current local minute; if that version is not later than existing versions, the
generator advances to the first available later minute. Consequently, a version
can be later than the actual creation time. Each up/down pair shares a version.
Existing migrations are never renamed or overwritten. Existing numeric sequential
versions such as `1`, `2`, and `3` are supported. If a greater version cannot be
followed using the minute format, for example a 14-digit timestamp with seconds,
the command reports the conflicting file and writes nothing. Do not rename
already-applied migrations without a database migration strategy.

### Custom migration

```sh
capg migration add_product_price
```

Creates a pair of SQL files containing placeholder comments. Replace both
comments with the forward and rollback SQL before applying the migration; an
unchanged placeholder performs no schema change. The name must start with a
lowercase ASCII letter and contain only lowercase letters, digits, and
underscores; `types` and `users` are reserved. Missing base migration support is
created as needed. The command uses the same version ordering as entity
migrations and never executes SQL.

## Migrations and database connection

The generated connection function only connects; it never applies or rolls back
migrations. The generated migration functions accept a path such as
`migrations/pg/migrations`, relative to the application's working directory.
Arrange for the application to run from the project root, or provide the correct
path for your deployment.

The initial SQL migration defines `text*` domains and fails if they already exist.
Review existing migrations and schema before applying new ones. Down migrations
can remove tables, domains, and data.

### Running migrations explicitly

Call `pg.MigrationUp(ctx, conn.DB, path, 0, false)` to apply all pending migrations,
or pass a positive step count to limit them. `pg.MigrationDown(ctx, conn.DB, path,
steps, false)` explicitly rolls back a positive number of steps; `pg.Migration(ctx,
conn.DB, path, false)` applies all pending migrations. None is called by `db.Connect`.

The context controls connection acquisition and requests a graceful stop when
cancelled. The migration driver stops between migrations; it cannot interrupt an
SQL statement already running or guarantee immediate cancellation while acquiring
a migration lock or initializing the driver. A cancelled call returns the context
error after the current operation finishes. Some migrations may already have been
applied or rolled back; inspect the migration state before retrying.

**Down migrations can destroy data.** The `force` argument clears the dirty
state at the recorded version without verifying the actual schema; it does not
execute or repair SQL, and can fail if no migration version exists. Back up and
inspect the schema and migration state before rolling back or forcing.

## Limitations and recovery

- Table names are derived mechanically: uppercase ASCII letters within a name
  become underscore-separated lowercase letters, then `es` is appended for
  names ending in `s`, `x`, or `h`; a final `y` becomes `ies`; otherwise `s` is
  appended. For example, `OrderItem` becomes `order_items` and `URL` becomes
  `u_r_ls`. This is not an English inflector: use `--table` when needed.
- JSON array and structure definitions are examples. Edit their generated Go
  types to match the JSON stored by your application; review existing data and
  database constraints when changing them.
- Generation plans and validates files before writing, never overwrites existing
  files, and attempts to remove files created by the current command if a write
  fails. Empty directories may remain. A process crash or rollback failure can
  still require manual recovery; inspect the error and existing files first.

## Testing

```sh
make test
make test-integration
```

The integration target requires Docker and starts a disposable `postgres:18`
container with a randomly assigned localhost port. It removes the container when
the test finishes. The generated project resolves its dependencies via Go
modules; the first run may need network access.
